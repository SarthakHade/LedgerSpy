## Bugs found and fixed during P4

1. **SQLite thread check (latent since P2).**
   - The dashboard's parallel requests produced HTTP 500 `SQLite objects created in a thread can only be used in that
     same thread`. FastAPI ran the per-request `get_db` dependency's setup and teardown on different worker threads.
   - Fix: `check_same_thread=False`. Each connection still belongs to exactly one request.
   - Regression test: `test_concurrent_requests_on_a_real_server` sends 60 parallel requests to a real uvicorn server.
     It fails without the fix.
2. **Bulk accept overrode a rejection (dashboard).**
   - "Accept all safe fixes" also selected fixes the analyst had *rejected*.
   - It now targets only undecided (`proposed`) fixes; check D2 covers it.
   - The live audit log shows the whole episode, including the revert of the mistakenly applied transformation.
3. **Severity rule.** In a first PaySim run, prevalence escalation lifted the synthetic INFO override back to ERROR
   (readiness 92.7, driven purely by simulator artefacts). A synthetic override is now final, as documented in config.

## Deviations from `architecture.md` / `roadmap.md` (recorded in `architecture.md`)

1. **The normalised dataset is an overlay.** §2 had *Normalize* produce the canonical tables. Here the P3 canonical
   rows stay the immutable, typed mapping of the evidence, and `normalized_values` holds logged overrides. That makes
   every difference explainable, and reversal exact and cheap.
2. **Integrity reports live in `integrity_runs` / `integrity_issues`**, not in `datasets.integrity_json`. Runs are
   immutable history, and P3 freezes canonicalised dataset rows.
3. **More endpoints than the contract listed:** `POST …/integrity`, `…/integrity/issues`, `…/fixes`,
   `…/fixes/decisions`, `…/transformations`, `…/transformations/{id}/revert`, `GET /api/datasets`.
   `GET …/transactions` gains `view=normalized|canonical`.
4. **Frontend boundary.**
   - Only the Data Integrity tab gets a backend panel (`frontend/js/integrity-panel.js`, ~280 lines, API data only).
     The rest of the UI stays the P1 in-browser preview until P9.
   - Datasets still reach the backend through the API; the frontend upload is P9.
   - The P1 preliminary in-browser readiness card remains, labelled as such. Its disabled "Auto-Fix" button now points
     to the backend panel, whose **✨ Auto-Fix** applies accepted fixes.
5. **P2/P3 compatibility changes, each strictly required:**
   - `check_same_thread=False` (bug 1).
   - Shared `LedgerSpyError` base class (`IngestError` now subclasses it).
   - Immutability triggers on P3 tables (`transactions` canonical columns, `ingest_issues`, `labels`).
   - `PaySimConverter.NOT_APPLICABLE` declares the corporate fields the simulation lacks.
6. **Checks beyond the requested list:** `field_coverage` (expected vs not-applicable fields), `needs_normalization`
   and `implausible_date`. The definitions the roadmap left open:
   - Exact duplicates compare all canonical fields but not `extra`; PaySim's pandas index column would otherwise make
     every row unique.
   - Near duplicates use a 3-day window, on the simulated clock for PaySim.
   - Balance continuity is PaySim per-row arithmetic, or for generic ledgers a running-balance column with an inferred
     sign convention, refusing to guess when it is inconclusive.

## Known limitations (deliberate)

- **Excluding rows.** Duplicate rows and rows with missing required values cannot be excluded or corrected in P4;
  there is no fix that would invent or delete data. Excluding rows from analysis is an investigation decision (P15).
- **Running-balance column.** Exactly one recognised running-balance column is supported per generic ledger.
- **Amount reinterpretation.** It covers the `amount` column only, not separate debit/credit columns.
