# LedgerSpy Public Demo: Deployment Checklist (free tier, synthetic data only)

This checklist is for the **public demo only** (`python -m ledgerspy_demo`, built from `deploy/demo/Dockerfile`).
It never deploys the offline application, whose `ledgerspy serve` stays loopback-only. Nothing here has been
deployed by the code: every external step is yours to do by hand. Budget: ₹0. Do not attach a payment method,
start a paid trial or upgrade a plan.

## 1. Decide before publishing

- **Synthetic data only.** The demo is not production software for real ledgers. The banner says so on every
  page, but it cannot stop anyone uploading real data.
- **Without persistence** (no storage settings): every sleep, restart or redeploy of the free instance deletes
  all visitor workspaces, and the UI says "This demo does not save workspaces". That is acceptable for a
  public demo; if you need saved work, configure persistence (§3) **before** publishing the link.
- **With persistence**: work is saved best-effort, a few tens of seconds after it changes, for at most 7 days.
  Changes made since the last save are lost on a restart; the UI tells the visitor when changes are not saved.

## 2. Render (free web service, Docker)

1. In Render, create a new **Blueprint** from this repository's branch (it reads `render.yaml`), or a Web
   Service with runtime Docker, Dockerfile `./deploy/demo/Dockerfile`, context `.`, instance type **Free**.
2. Environment (Render dashboard → Environment):

| Variable | Required | Value |
|---|---|---|
| `LEDGERSPY_DEMO_SESSION_KEY` | yes | generated by Render (`generateValue`); never copy it anywhere else |
| `LEDGERSPY_DEMO_PUBLIC_ORIGIN` | yes | `https://<your-service>.onrender.com` (exact origin, no path, no trailing slash) |
| `LEDGERSPY_DEMO_TRUSTED_PROXY_HOPS` | no (default 0) | keep `0` unless you have verified how Render's proxy writes `X-Forwarded-For` (§6) |
| `LEDGERSPY_DEMO_STORAGE_URL` | persistence only | `https://<project-ref>.supabase.co` |
| `LEDGERSPY_DEMO_STORAGE_BUCKET` | persistence only | the private bucket's name |
| `LEDGERSPY_DEMO_STORAGE_SERVICE_KEY` | persistence only | the Supabase **secret key** (`sb_secret_…`; a legacy `service_role` JWT also works); never a publishable key |
| `LEDGERSPY_DEMO_<LIMIT>` | no | stricter limits only (see `ledgerspy_demo/limits.py`) |

   Set by the image (do not change): `LEDGERSPY_MODE=demo`, `LEDGERSPY_DEMO_DATA_DIR`,
   `LEDGERSPY_DEMO_SEED_DIR`, `LEDGERSPY_DEMO_BIND_HOST=0.0.0.0`. Render sets `PORT`.
   The three storage variables are all-or-none: a partial set stops the service at start-up (fail closed).
3. Health check path: `/healthz` (in `render.yaml`). It answers a fixed `{"status":"ok"}` and nothing else.
4. Deploy manually (`autoDeploy: false`). Check the logs show
   `LedgerSpy public demo on https://<service>.onrender.com`, then open the URL: the landing page must show the
   synthetic-data warning, and "Start a demo workspace" must open the app.

## 3. Supabase Storage (optional persistence; Free plan)

1. Create a project on the **Free** plan (no payment method).
2. Storage → New bucket → name it (e.g. `ledgerspy-demo-snapshots`) and leave **Public bucket OFF**. The demo
   checks this at start-up and **refuses to use a public bucket** (persistence is then reported as disabled).
3. Optional: set the bucket's file size limit to 32 MB (a snapshot is at most 25 MiB plus archive overhead).
4. Project settings → API keys: copy a **secret key** (`sb_secret_…`) into Render's
   `LEDGERSPY_DEMO_STORAGE_SERVICE_KEY` (it is sent only in the `apikey` header, as Supabase requires). It bypasses Row Level Security, so it must stay server-side: never in
   a browser, a repository, `render.yaml`, a Docker build argument, a screenshot or a log.
5. No policies are needed (the server uses the secret key; nothing in the browser talks to Supabase).

Objects are written only under `workspaces/<W-id>/` (`snapshot-<generation>.zip`, `manifest-<generation>.json`)
with create-only uploads. Expired workspaces (7 days) and orphaned uploads (older than a day without a pointer)
are deleted hourly by the service itself.

## 4. After deploying: verify

- `https://<service>/healthz` → `{"status":"ok"}`.
- Landing page → "Start a demo workspace" → the app opens with the banner and the save status line.
- With persistence: change something, wait about a minute, the status line says "All changes so far are saved".
- `https://<service>/demo/status` shows `"persistence": "ready"` (or `"disabled"` / `"unavailable"`).
- Supabase Storage shows objects only under `workspaces/W-…/`, and the bucket is private.

## 5. Free-tier facts (checked 2026-10-19; re-check before each deployment)

- **Render Free web services** spin down after 15 minutes without inbound traffic and take up to about a minute
  to wake; their filesystem is ephemeral (local changes are lost on every restart, redeploy or spin-down); Free
  services cannot use persistent disks; 750 free instance hours per workspace per month, after which free
  services are suspended until the next month. Source: <https://render.com/docs/free>,
  <https://render.com/docs/faq>.
- **Supabase Free**: 1 GB file storage per project, free projects pause after one week of inactivity (restore
  by hand from the dashboard; while paused, restores fail and the demo says the saved copy cannot be fetched),
  limited egress. Source: <https://supabase.com/pricing>.
- Free tiers and their limits change without notice. There is no SLA, no guaranteed persistence and no
  guaranteed availability.

## 6. Known limits and open points

- The demo keeps everything in one process on one instance; do not scale it to two instances (no shared lock).
- Client identity for per-client creation limits: with `TRUSTED_PROXY_HOPS=0` every visitor behind Render's
  proxy shares one key, so the per-client limit acts as a second global limit; the service-wide limits hold
  regardless. Change it only after verifying Render's `X-Forwarded-For` behaviour (not verified here).
- The persistence code has been tested against an in-memory fake of the Supabase Storage API (create-only
  uploads, listing, deletion, bucket privacy, failures). It has **not** been run against a real Supabase project
  from this repository; do the checks of §4 before relying on it.
