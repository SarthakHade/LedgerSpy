# LedgerSpy Public Demo: Design (Stage 3: optional best-effort persistence; deployment files)

**Status.** Stage 2 (isolated visitor workspaces, hardened through Stage 2.11) and Stage 3 (optional snapshot
persistence to a private Supabase Storage bucket, a Docker image and a Render Blueprint) are implemented and
tested locally: on Windows, on Linux (WSL Ubuntu 24.04) and inside the Linux container image. **Nothing is
deployed.** Persistence has been tested only against an in-memory fake of the Supabase Storage API, never against
a real Supabase project; until that is done (deployment checklist §4), treat it as unverified in production.
Setup: [deployment-checklist.md](deployment-checklist.md).

**What this is.** A public demonstration on **synthetic data only**. It is not production software and must not
be used for real client ledgers, personal data or confidential data. On the intended host (Render free web
service) the instance sleeps when idle and restarts on deploys, and its local disk is not durable. Without
storage settings every workspace is lost on each of those events; with them, workspaces are restored from their
latest saved copy, and changes made since that save are lost. Nothing is guaranteed: no SLA, no durability.
- **This document:** the architecture, the request flow and isolation boundary, the visitor-workspace lifecycle,
  cache isolation, limits, persistence (§4.2–4.3, §9), failure behaviour, secrets, and hosting risks.
- **Code:** the package `ledgerspy_demo/` (never shipped offline) and `ledgerspy/cache.py` (the engines'
  per-database caches, shipped offline). Tests: `tests/demo/` (run with `python -m pytest tests/demo`).

The hosted demo is for **synthetic data only**. It is not a service for real client data, and nothing here
supports or encourages that. **Without storage settings, work is not saved across service restarts**; with
them it is saved best-effort (§4.2). Either way it is deleted after at most 7 days.

## 1. Non-negotiables

1. **The offline application stays the default and is unchanged:**
   - loopback-only binding (`server.host` must be `127.0.0.1`; `build_server` refuses anything else);
   - the per-launch token; Host / Origin / Fetch-Metadata checks; the strict CSP;
   - `config/default.yaml` and the offline bundle's allow-list.

   Demo code lives in `ledgerspy_demo/`. The offline package never imports it (tested), and the bundle builder
   never collects it or `docs/demo/` (tested). The only change to the offline package is that the engines' result
   caches are partitioned per database (`ledgerspy/cache.py`, §5); with one database the behaviour is unchanged.
2. **Demo mode is explicit:** `LEDGERSPY_MODE=demo` plus its required settings. Without them, demo settings
   refuse to load and `python -m ledgerspy_demo` exits with status 2.
3. **Identity and paths are server-side:**
   - workspace IDs are generated by the server, carried only in an HMAC-signed cookie, and checked before use;
   - a visitor-supplied ID, path or object key is never used.
4. **Uploads stay private.** Visitor uploads never go to a public bucket or a public URL. Evidence is never
   served as a file; PDF pages are rendered through the authenticated API, as offline.
5. **No security control is weakened to deploy.** Each workspace keeps its own bearer token, CSP and request
   bounds; the front door adds checks and never removes one.
6. **No guarantee of persistence.** Stage 2 keeps nothing across restarts, and says so in the banner. A
   workspace that cannot be used is shown as a failure, never replaced by an empty one under the same ID.
7. **Budget: ₹0.** Free tiers only (Render free web service, Supabase Free Storage). There is no paid fallback.

## 2. Architecture

```
browser ──HTTPS──> TLS-terminating proxy (Render) ──> uvicorn (one process, one worker, proxy_headers off)
                    └─ demo front door  ledgerspy_demo.frontdoor.FrontDoor
                        ├─ Host must equal the public host; Origin (if sent) must equal the public origin;
                        │  Sec-Fetch-Site must be same-origin / none (a cross-site navigation to / gets a bounce page)
                        ├─ signed cookie ls_demo_ws → workspace ID (only POST /demo/workspace/new creates one)
                        ├─ WorkspaceManager: lease the workspace's resident app (open + verify if needed)
                        ├─ limits: request rate, uploads, sizes, workspace quota, service budget
                        ├─ per-workspace asyncio.Lock (every request, reads included, one at a time)
                        └─ forward to that workspace's own, UNCHANGED ledgerspy.api.app.create_app(...) instance
                             ├─ its own SQLite file   <DATA_DIR>/workspaces/<W-id>/ledgerspy.db
                             ├─ its own evidence/, reports/, inference/, tmp/
                             └─ its own bearer token, LocalSecurityMiddleware (token, Host, body bound), CSP
```

**Why per-workspace app instances.** `create_app(config, db_path, token)` already binds one database, one
workspace folder and one token per app instance (`app.state.config`, `db_path`, `workspace`, `actor`). Every
route reads only these. A bounded registry of instances gives each visitor an isolated application without
changing any of the 14 route modules and without a global "current workspace" switch.

**Actor.** Each workspace app's audit actor is `demo:<first 8 hex of the workspace ID>`. It is never an OS user
name or an IP address.

### 2.1 Request flow and the isolation boundary

1. **Public checks.** The Host header must equal the host of `LEDGERSPY_DEMO_PUBLIC_ORIGIN` (otherwise `400`); an
   `Origin` header must equal the origin (`403`); `Sec-Fetch-Site` other than `same-origin` / `none` is refused
   (`403`), except a top-level navigation to `/`, which gets a same-origin bounce page and no workspace.
2. **Workspace binding.** The only source of a workspace ID is the `ls_demo_ws` cookie
   (`<W-id>.<issued-at>.<HMAC-SHA256>`, `Secure; HttpOnly; SameSite=Strict; Path=/`, max-age = retention). It is
   verified with the server key and its age checked before the ID is used. A missing, malformed, forged, tampered
   or expired cookie is no cookie: a page view (`GET`/`HEAD` of `/`) gets a static landing page and allocates
   nothing (Stage 2.11); only the landing page's same-origin `POST /demo/workspace/new` creates a workspace;
   anything else gets
   `401 no_demo_workspace`. IDs in paths, queries or bodies are never used to choose a workspace.
3. **Leasing.** `WorkspaceManager.lease(wid)` returns that workspace's resident app, or opens it: it checks the
   folder, metadata and expiry, verifies the audit chain, triggers and evidence, then builds the app. A workspace
   that cannot be used raises `WorkspaceUnavailable`; it is never replaced.
4. **Forwarding.** The front door drops `Host`, `Origin`, `Cookie`, `Forwarded` and `X-Forwarded-*` / `X-Real-IP`,
   presents the inner app's loopback Host (and a loopback Origin when one was sent), and never adds an
   `Authorization` header. For the page only (`GET`/`HEAD` of `/` or `/index.html`) it adds the inner app's
   session cookie, which makes the inner app put the workspace token in the page, exactly as the offline entry
   link does. Every API call must carry that token as `Bearer`, checked by the unchanged inner middleware.
5. **Inside the workspace app** every route uses only its own `app.state`. Any ID in a request (case, dataset,
   run, investigation, report, model, inference, PDF item, master file) is looked up in **that** workspace's
   database or folder, so another workspace's ID is simply not found.

**Where an ID could reach another workspace (Stage 2 analysis).**

| Path | State touched | How a foreign ID is handled |
|---|---|---|
| Route families: `cases`, `datasets`, `quality`, `forensics`, `anomaly`, `risk`, `resolution`, `graph`, `reconciliation`, `pdf`, `investigations`, `reports`, `models`, `health` | the workspace app's own `config`, `db_path`, `workspace`, `actor` | looked up in the workspace's own database / folder → the same `404` / `409` / `422` as an ID that never existed (tested per family, bodies compared after masking the ID) |
| Process-wide result caches (`risk`, `resolution`, `graph`, `reconciliation`, `supervised.inference`) | module-level, shared by all instances | **were** keyed by content identity / run ID only. Now partitioned per database (§5): a foreign run ID is `404 run_not_found` and never touches the owner's entry |
| String-similarity `lru_cache`s (`resolution.similarity`) | pure functions of two strings | shared; hold no records, IDs or results. At most a timing signal about which names were compared recently (acceptable for synthetic data) |
| `cases.db.expected_triggers`, `detectors.rules.RULES`, `features.spec.REGISTRY` | schema / code constants | no workspace data |
| Workspace ID itself | cookie only | signed and verified; never taken from a path, header, query or body |
| Workspace token | per workspace (`HMAC(server key, "ledgerspy-demo-api-token-v1" ‖ W-id)`) | another workspace's token is refused by the inner app (`401`); a token is served only in its own workspace's page |

**Limits of this design.**
- **Shared process.** All instances share one Python process: memory, CPU and the module-level caches (§5). At
  most `max_resident_workspaces` app instances are open; idle ones are closed (LRU) and their cache entries
  dropped.
- **One instance only.** A single Render instance is assumed. Two instances would need a cross-instance lock and
  shared storage, which this design does not provide.

## 3. Visitor-workspace lifecycle (Stage 2: local and ephemeral)

| State | Entered when | Behaviour |
|---|---|---|
| `NEW` | a same-origin `POST /demo/workspace/new` (Origin required, Fetch-Metadata checked), within the per-client, service-wide and capacity limits | The server generates `W-<32 hex>`, copies the read-only **seed** into a temporary folder, writes `workspace.json` and renames it into `<DATA_DIR>/workspaces/<W-id>/`, then sets the signed cookie |
| `ACTIVE` | Created, or opened and verified | Requests are served one at a time under the workspace lock |
| `CLOSED` | Evicted because more than `max_resident_workspaces` are open (idle ones only, least recently used) | Files stay on disk; the next request reopens and re-verifies it. The workspace token is stable, so an open page keeps working |
| `UNAVAILABLE` | The folder or metadata is missing (e.g. after a restart on an ephemeral disk), the metadata is unreadable, or verification fails | `409`: a page "Your demo workspace cannot be used: <reason>" with **Start a new demo workspace** (a new ID), or JSON `workspace_restore_failed`. Files are kept until expiry; **no empty workspace is ever created under the old ID** |
| `EXPIRED` | `retention_days` after creation | The cookie is no longer accepted; the visitor sees the landing page and may start a new workspace (a new ID). Cleanup deletes the folder once it is idle |

**Seed.** At start-up `build_seed` imports the synthetic company (`data/synthetic/reference/`, no ground-truth
files) through the normal services into a temporary folder, verifies it (audit chain, triggers, evidence), writes
`seed.json` and renames it into place; a later start reuses a seed that verifies. It is about 9 MiB. A new
workspace is a copy of the seed only, **never** of another visitor's workspace (tested).

**Cleanup.** At start-up and before each workspace creation: expired workspace folders are deleted unless the
workspace is in use, and abandoned `.W-*` temporary folders older than an hour are deleted. Only folders whose
names are server-generated IDs are touched.

## 4. Concurrency, snapshots and restoration

### 4.1 Serialisation (implemented)

- **One lock per workspace,** held for the whole request: every request to a workspace runs under it, reads
  included. A waiting request has a bounded wait (`lock_wait_seconds`), then gets `503 workspace_busy`.
  Concurrent reads are not enabled: no test demonstrates them to be safe, and on 0.1 CPU they would not help.
- **Creation and eviction under one guard.** `WorkspaceManager` takes one manager-wide lock for creating,
  opening, evicting and sweeping. A workspace is leased **before** eviction runs, so a new or reopened workspace
  is never its own victim, and an in-use workspace (leased or locked) is never closed. Two simultaneous first
  requests for the same closed workspace therefore produce one app instance. When every resident instance is in
  use, opening another is refused (`503 demo_busy`) rather than exceeding the bound.
- **Limits under the lock (Stage 2.6).** Only checks of the request itself (rate, declared size) run before
  the lock. Everything that depends on the workspace's state — the upload count, the hourly upload limit,
  the quota (measured on disk at that moment) — is checked after the lock is acquired, and an accepted upload
  is counted before the lock is released. Concurrent requests to one workspace therefore never pass these
  checks on a stale count or size (tested with forced interleavings).
- **Service-wide storage reservations** (`ledgerspy_demo/budget.py`). Every request reserves its enforced
  storage bound (§6.1; Stage 2.8) and every workspace creation the seed's size, atomically:
  `measured usage + outstanding reservations + request + head-room ≤ budget`, else `507 demo_storage_full`.
  Usage is re-measured on each admission, so writes count at their real size; the reservation is released
  exactly once, when the work (and any worker thread or subprocess) can no longer write. Temporary files go to
  a marked run folder in `<data>/tmp` (§6.2) and are measured too. The head-room is not relied on to absorb
  any growth: every write path has an enforced bound.
- **Lock order.** The manager's guard and a workspace lock are never awaited while the other is held by the
  same task. The budget's lock is a leaf, held only for its arithmetic and never across an `await`.
- **Processing time (Stage 2.6).** A request without an answer after `max_processing_seconds` cannot be
  stopped safely (a worker thread may be committing), so it is not cancelled:
  - it keeps the workspace lock and its reservation until it really ends, and its outcome is then counted
    (an upload that succeeds late counts against the upload limits);
  - the visitor gets `504 still_processing` ("may still complete; do not send it again"), never a failure;
    a read gets `504 processing_timeout` (its answer was discarded);
  - while it runs, further state-changing requests to that workspace get `409
    previous_request_still_processing` at once. A request cancelled by the server (e.g. a dropped connection)
    is handled the same way.
- **Retries (Stage 2.11).** A state-changing request may carry `Idempotency-Key` (8–64 of `A–Z a–z 0–9 - _`).
  The key is tied to the workspace and to the method, path, *sorted* query and a SHA-256 of the body, computed
  while the body streams (never buffered). Same key and same request: the recorded result is replayed
  (`Idempotent-Replayed: true`) without running again; while it still runs, `409
  idempotent_request_in_progress`; same key with anything different: `409 idempotency_key_reused`. Entries
  expire after `idempotency_ttl_seconds` (10 min), at most 16 per workspace (oldest finished first), answers
  above 64 KiB are kept by status only; all in memory, never logged. Without a key there is no deduplication:
  the earlier address-only matching refused different requests to the same route and was removed. (The offline
  UI sends no key.)
- **PDF worker jobs (Stage 2.11).** Requests that run the PDF worker (a bank-statement upload, re-extraction,
  a page image) take one of `max_concurrent_pdf_jobs` (1) service-wide slots after their workspace lock, waiting
  at most `lock_wait_seconds` (`503 pdf_busy`), and release it only when the work has ended. Each worker runs in
  its own process group (POSIX session / Windows process group) with its own folder under `<run>/workers`, also
  passed to Tesseract (`TMPDIR`/`TEMP`/`TMP`); on its timeout the whole tree is killed (`killpg` / `taskkill
  /T`), and the folder is deleted only once the tree has exited (on POSIX: once no process of the group is
  left).
- **Graceful shutdown (Stage 2.11).** On SIGTERM / SIGINT (Ctrl+Break on Windows) new requests get `503
  shutting_down`; running work, including work that outlived its request, is waited for up to
  `shutdown_grace_seconds` (25); then PDF worker trees are killed and the rest waited for briefly. Locks and
  reservations are released only by the work itself; temporary folders of a killed run are removed at the next
  start (after its lock is taken).
- **One process and one worker.** Together with the lock, a workspace has a single writer. SQLite's 30 s busy
  timeout (P24) still covers background readers.

### 4.2 Snapshots (Stage 3, implemented: `ledgerspy_demo/persistence.py`, `snapshots.py`, `storage.py`)

Persistence is on only when all three storage settings are present and valid **and** the bucket reports
itself private at start-up (`GET /bucket/<name>`); a public bucket turns persistence off for good, an
unreachable one makes it "unavailable" (retried every 5 minutes). Otherwise it is "disabled" and the UI says
that work is lost on restart.

**What is saved.** A zip archive per generation: the database, copied with SQLite's online backup API (never
the live file), plus the allow-listed persistent files (`workspace.json`, `seed.json`, `evidence/<sha256>.<ext>`,
`reports/RP-….(html|json|md)`, `inference/I-….json`), and a manifest `snapshot.json` (format, version,
workspace ID, generation, schema version, creation times, each file's size and SHA-256). Never temporary files,
journals, locks, backups or caches.

**When.** A single background task, one transfer at a time: a workspace with unsaved changes is saved after
`snapshot_quiet_seconds` (20) without changes, or at the latest `snapshot_max_delay_seconds` (120) after its first
unsaved change. Failures back off (30 s, doubling, at most 10 minutes). Unsaved means: a state-changing request
reached the workspace app after the newest stored snapshot was taken (a change counter, so a write made during an
upload is never reported as saved).

**How (lock scope).**
1. Under the workspace's persistence lock (serialises that workspace's snapshots and restores, nothing else),
   the newest stored generation is read once per process (never reusing a generation after a restart).
2. The workspace's request lock is taken (bounded wait) only while the local copy is made; the visitor's
   requests are blocked for that copy only, never for the network transfer. No global lock is held while
   transferring.
3. The budget reserves 2 × the workspace's size + 1 MiB for the copy and archive (in the run's temporary folder).
4. Upload `workspaces/<W-id>/snapshot-<generation>.zip`, then the pointer `manifest-<generation>.json`
   (`archive`, `archive_sha256`, `archive_bytes`, `created_at`, `workspace_created_at`), both **create-only**
   (`x-upsert: false`): an existing key is a conflict, never overwritten. A conflict (another writer) re-reads the
   generation and retries later. Generations only increase and restore uses the highest, so an older upload can
   never replace a newer snapshot.
5. Only after the pointer is stored is the workspace "saved"; generations older than the previous one are then
   deleted. An interrupted upload leaves the previous generation as the current one.

**Eviction and shutdown.** A workspace with unsaved changes is never closed (it is not "idle"); when every
resident slot holds such a workspace, new workspaces get `503 demo_busy` until a save completes — work is never
dropped to make room. At shutdown, after running requests end, changed workspaces are saved until the grace
period ends (`shutdown_grace_seconds`, measured from the stop signal); the rest are reported as not saved.

**Failures.**

| Situation | Behaviour |
|---|---|
| Storage unreachable, timeout, 5xx | bounded retries (2, then back-off); status "failed"/"unavailable"; nothing reported as saved |
| 4xx (key, bucket, request) | not retried immediately; back-off; status "failed" |
| Budget full | no snapshot; status stays "pending"; retried |
| Process killed mid-snapshot | the run's temporary folder is removed at the next start-up; storage keeps the previous complete generation |
| Pointer conflict | this writer stops; the newer generation stands |

### 4.3 Restore (Stage 3, implemented)

On the first access to a workspace whose local folder is missing (after a restart, a sleep or a redeploy), the
request's lease restores it — outside the manager's guard, single-flight per workspace:

1. List `workspaces/<W-id>/`; take the highest pointer; validate it (format, workspace ID, generation, archive key,
   sizes ≤ the quota). No pointer → the workspace is reported lost (never replaced by an empty one).
2. Retention: `workspace_created_at` (written by the server) older than `retention_days` → expired.
3. Reserve, download the archive (capped at its recorded size), check its SHA-256.
4. Extract into a fresh staging folder with full validation: allow-listed names only, regular files only (no
   symbolic links, directories, absolute paths, `..`, backslashes, duplicates, encrypted entries), bounded count
   and total size, each file streamed with its size capped and compared with the manifest's size and SHA-256.
5. Verify the database and evidence (`verify_workspace`: audit chain, triggers, evidence hashes and read-only
   state); then rename the folder into place atomically and open it normally (which verifies again).

A damaged or incompatible copy marks the workspace unavailable with its reason (kept until expiry); a storage
outage is reported as temporary ("try again in a minute") and retried after a back-off. Staging folders are
removed on every failure; the active workspace is never overwritten.

**Visible status.** `GET /demo/workspace/status` (the visitor's own workspace, by cookie) returns `disabled`,
`pending`, `saved`, `failed` or `unavailable`, whether there are unsaved changes, and the time of the last save;
the banner shows it (`js/demo-status.js`, same origin, text only). Snapshots are never served by any route.

## 5. Cache isolation (implemented)

**Inventory of process-wide state with workspace data** (all other module-level state is code or schema
constants, §2.1):

| Cache | Key before | Now |
|---|---|---|
| `risk.service._CACHE` (4) | content identity of the dataset | per database: `NamespacedLRU`, namespace = main database file |
| `resolution.service._CACHE` (4) | content identity | per database |
| `graph.service._CACHE` (6) | content identity + window | per database |
| `reconciliation.service._CACHE` (`max_runs_cached`) | `run_id` | per database; `get_run` looks only in its own namespace |
| `supervised.inference._CACHE` (4) | `inference_id` | per workspace folder; `read_metadata` looks only in its own namespace |

**What the old keys allowed in a shared process.** Workspaces copied from one seed share dataset IDs and data,
so identical content identities would have served one workspace's cached result to another. A foreign
`inference_id` returned the other workspace's inference metadata from the cache, and a foreign reconciliation
`run_id` produced `409 inputs_changed` (revealing that the run exists elsewhere) and could evict the owner's
entry.

**Now** (`ledgerspy/cache.py`): every entry is stored under the database (or workspace folder) it was computed
from; lookups, evictions and the per-namespace size bound apply within one namespace only; at most 64 namespaces
are kept. When the demo closes a workspace it forgets both of its namespaces. Offline there is one namespace, so
the behaviour is that of one LRU of the same size, as before (the full backend suite is unchanged and passes).
`clear_cache()` still clears everything.

**Tests** (`tests/demo/test_demo_isolation.py`): B cannot obtain A's risk, resolution, graph, reconciliation or
inference results, even with A's IDs; B's lookups leave A's entries in place; a foreign run ID gets the same
`404 run_not_found` as a made-up one; each namespace is bounded separately; closing a workspace forgets its
entries.

## 6. Limits (configurable; stricter than offline, never looser)

The defaults are in `ledgerspy_demo/limits.py` and can be overridden with `LEDGERSPY_DEMO_<NAME>`:
- an override is validated, never clamped;
- `check_against_offline` refuses any value above the offline equivalent;
- `config/default.yaml` is unchanged; the workspace apps get the stricter values as configuration overrides.

|---|---|---|---|
| `max_upload_bytes` | 2 MiB | 100 MiB (`ingest.max_file_bytes`) | front door (declared `Content-Length`; a missing one is `411`), and the workspace app's streaming limit (the real bytes) |
| `max_rows` | 20,000 | 1,000,000 (`ingest.max_rows`) | workspace app configuration |
| `max_pdf_pages` | 5 | 200 (`pdf.max_pages`) | workspace app configuration |
| `pdf_worker_timeout_seconds` | 120 | 900 | workspace app configuration |
| `max_uploads_per_workspace` | 10 | none | front door (counted in `workspace.json`) |
| `uploads_per_hour` | 10 per workspace | none | front door |
| `requests_per_minute` | 60 per workspace | none | front door |
| `max_processing_seconds` | 120 | none | front door (§4.1) |
| `lock_wait_seconds` | 30 | — | front door |
| `max_workspace_bytes` | 25 MiB | none | under the workspace lock: measured, then enforced by the database cap and file limits (§6.1) |
| `storage_budget_bytes` | 800 MiB (includes seed, UI copy, temporary files) | — | reservation of every request's enforced bound and of each creation (§4.1, §6.1), plus one workspace's worth of head-room |
| `max_pdf_render_pixels` | 12,000,000 | 40,000,000 (`pdf.render.max_pixels`) | workspace app configuration; the PDF worker's file-size limit |

| `max_active_workspaces` | 20 (on disk) | — | creation |
| `max_resident_workspaces` | 2 (open app instances; 512 MB host) | — | registry (§4.1) |
| `new_workspaces_per_hour_per_client` | 5 | — | creation (client identity, see below) |
| `new_workspaces_per_hour` | 20, service-wide | — | creation (cannot be escaped by any client identity) |
| `max_columns` | 64 | 512 (`ingest.max_columns`) | workspace app configuration |
| `xlsx_max_uncompressed_bytes` / `xlsx_max_zip_entries` | 16 MiB / 100 | 500 MiB / 10,000 | zip directory checked before openpyxl parses anything |
| `max_concurrent_pdf_jobs` | 1, service-wide | — | front door (§4.1) |
| `idempotency_ttl_seconds` | 600 | — | front door (§4.1) |
| `shutdown_grace_seconds` | 25 | — | lifespan shutdown and uvicorn's connection drain |

**Types.** Uploads stay CSV, XLSX and PDF, with the existing P3 / P14b / P20 parsers and refusals. A ZIP or any
other archive is refused as an unsupported format (an XLSX is read only as a spreadsheet). Visitors cannot
upload snapshots or archives of any kind.

**Client identity for rate limits.**
- **Default (`LEDGERSPY_DEMO_TRUSTED_PROXY_HOPS=0`):** the TCP peer address. Forwarded headers are ignored, and
  uvicorn runs with `proxy_headers` off, so a client cannot choose its apparent address.
- **Behind a known proxy chain (`=N`, 1–3):** the N-th address from the right of `X-Forwarded-For`, i.e. the one
  written by the outermost trusted proxy; anything further left is client-controlled and ignored.
- The address is kept only as an HMAC with the server key, in memory, and is never stored or logged.

### 6.1 Storage bound of every request (Stage 2.8)

Every request is classified (`ledgerspy_demo/allowances.py`); a state-changing route without an explicit class
is refused (`403 operation_not_available`), and a test checks that every state-changing route of the workspace
app has one. Under the workspace lock, the request's plan is computed from the measured workspace and database
sizes, its whole bound is reserved, and the bound is enforced while it runs:

| Part | Bound | Enforced by | Status |
|---|---|---|---|
| Database growth | to `db_cap` = database + (quota room − the request's files) | SQLite `PRAGMA max_page_count` on every connection (`ledgerspy/storage_limits.py`); beyond it SQLITE_FULL, transaction rolled back, answer `507 storage_limit_reached` | proven (SQLite) |
| Reads | no database write at all | `PRAGMA query_only` | proven (SQLite) |
| Rollback journal (transient) | pages existing at transaction start × (page + 8) + one sector (≤ 64 KiB) ≤ `journal_bytes(db_cap)` | SQLite file format (each page journaled once per transaction) **and** `PRAGMA cache_spill = OFF` (Stage 2.10): without it, every cache spill starts a new journal segment with its own sector-sized header — measured 15.4 MB against a 12.4 MB bound with a 5-page cache | proven from the format, with spills off; tested with a tiny cache |
| SQLite temporary files | none on disk | `PRAGMA temp_store = MEMORY` | per SQLite documentation |
| Upload | its declared Content-Length (≤ 2 MiB), written once (staged, then moved into evidence) | only Content-Length framing is accepted: any `Transfer-Encoding` is refused with `400` before a workspace is reached (h11 would otherwise frame a chunked body and ignore Content-Length — Stage 2.9 B2); the front door also stops the body at the declared size | proven; tested through a real loopback server |
| Report artifacts | ≤ `max_report_bytes` (4 MiB) per report | refused before writing (`storage_limits.claim_output`) | proven |
| Inference result | ≤ `max_inference_bytes` (4 MiB) | refused before writing | proven |
| PDF page render (transient, one page at a time; upload of a bank statement, re-extraction, page image) | `2 × max_pdf_render_pixels + 1 MiB` per file | the PDF worker's `RLIMIT_FSIZE` (Linux); pages above `max_pdf_render_pixels` (12 Mpx) are refused | proven on Linux; **estimate on Windows** (not enforced there) |
| XLSX parsing | no temporary files | openpyxl's reader does not use temporary files (its writer does) | verified by code search |

A request's reservation is the sum of these parts. Its persistent growth (database + files) is at most the
workspace's remaining room, so the workspace never passes its quota. After the work has stopped, the database's
growth and the growth of everything else are each compared with their own part of the bound (Stage 2.10: file
growth can no longer hide inside the database's allowance); exceeding either (which should be impossible)
blocks further state-changing requests to the workspace (`507 workspace_storage_overshoot`, fail closed) and is
counted.

**Memory cost of `cache_spill = OFF`.** A transaction's dirty pages stay in memory until it commits: at most
about 1.2 × the database cap per writing connection (measured on Windows: +36.3 MiB while rewriting every page
of a 30.5 MiB database in one transaction; the offline default showed no increase). With the 25 MiB quota that
is about 30 MiB per workspace writing at that moment, and at most one write runs per workspace; six resident
workspaces rewriting their whole database at once would need about 180 MiB (relevant to the 512 MB host; see
§10). The offline application keeps SQLite's default (spills on).

**Calibration** (real app, largest allowed upload: 2 MiB, 9,890 rows): upload +2.00 MiB, mapping +4.84 MiB
(2.42 × the file), integrity +2.34 MiB, normalize +2.31 MiB, risk / forensics / anomaly 0; a bank
reconciliation report on the seed 0.81 MiB. The review's "4 × the upload size" was therefore plausible for a
single step, but a multiplier is not an enforced bound and was not adopted: the database cap enforces the
quota whatever an operation writes.

**Cost.** A state-changing request reserves its workspace's whole remaining room plus a journal as large as
its database cap (about 40 MiB for a fresh workspace). Near a full service, writes are refused
(`507 demo_storage_full`) earlier than strictly necessary; that is the price of not estimating.

### 6.2 The data folder and temporary files (Stage 2.8)

`ledgerspy_demo/datadir.py`; nothing is deleted unless every check holds, and doubt refuses to start:

- **Setting:** absolute; no `.`/`..`; not a file-system or drive root; not UNC, network or device paths; not a
  well-known system folder.
- **Folder:** no part of the path may be a symbolic link, junction or reparse point, and its resolved path
  must equal the lexical one; it must not be, or contain, the OS temporary folder, the home folder or the
  repository, nor hold an offline LedgerSpy database. It must carry the demo marker written for exactly that
  path, or be new / empty (the marker is then created with O_EXCL); a non-empty unmarked folder is refused.
- **Ownership (Stage 2.10):** one process per data folder. An exclusive lock on `<data>/.ledgerspy-demo.lock`
  (`fcntl.flock` / `msvcrt.locking`) is taken after the folder checks and before any cleanup, and held for the
  process's life; a second process fails closed and touches nothing (tested with two real processes). The
  lock is released on normal shutdown and on a failed start-up, and by the operating system if the process
  dies.
- **One configuration for every entry point (Stage 2.10):** `build_demo_app` configures the process itself
  (`configure_process`: folder checks, lock, temporary files, PDF worker limit), once; the folder is checked
  against the OS temporary folder as it was before the redirect. `python -m ledgerspy_demo` stops gracefully on
  SIGINT / SIGTERM (Ctrl+Break on Windows), releases the lock and exits with status 0.
- **Temporary files:** `<data>/tmp` needs its own marker; each process works in a new `run-<32 hex>` folder
  with a run marker naming it, and `TMPDIR` / `TEMP` / `TMP` point there (process-wide, inherited by the PDF
  worker). At start-up only earlier runs' folders proven by name, type and marker are removed; anything else
  in `<data>/tmp` is left alone, and `<data>/tmp` itself is never deleted.
- **Deletion** never follows a link: links and junctions are removed as links. On Linux it uses
  `shutil.rmtree`'s descriptor-based walk (safe against symbolic-link races); on Windows each entry is
  re-checked just before it is removed, and a race with a local writer inside the data folder remains possible.
- The demo's other deletions (an old UI copy, an old seed, expired workspaces, failed creations) use the same
  deletion, inside the validated folder.

## 7. Failure behaviour

| Failure | What the visitor sees | What the server does |
|---|---|---|
| Workspace lost (service restarted on an ephemeral disk) | "cannot be used: the workspace is no longer on this server …" + **Start a new demo workspace** | records the reason; never recreates the old ID |
| Workspace fails verification | the same page, with the reason | keeps the files until expiry, then cleanup deletes them |
| Limits exceeded | an explicit `411` / `413` / `415` / `429` / `503` / `507` with the limit named | nothing is half-imported (P3) |
| Too many workspaces | "The demo is at capacity" / "busy; try again shortly" | `503 Retry-After` |
| Request too slow | `504 still_processing` (state-changing: it may still complete) or `504 processing_timeout` (a read) | the work is not cancelled; the workspace stays locked and its storage reserved until it ends, then its outcome is counted |
| Out of memory or restart | lost work; the next visit shows the "cannot be used" page | the container restarts |
| Expired workspace | a new workspace on the next page visit | cleanup |

## 8. Secrets and environment variables

The variables are described in `ledgerspy_demo/settings.py`:
- `LEDGERSPY_MODE=demo`;
- `LEDGERSPY_DEMO_SESSION_KEY` (secret; signs cookies and derives workspace tokens);
- `LEDGERSPY_DEMO_DATA_DIR`;
- `LEDGERSPY_DEMO_PUBLIC_ORIGIN` (`https://…`; plain `http://` only for `localhost` testing);
- `LEDGERSPY_DEMO_TRUSTED_PROXY_HOPS` (0–3, default 0), `LEDGERSPY_DEMO_BIND_HOST` (`127.0.0.1` default, or
  `0.0.0.0` inside a container), `LEDGERSPY_DEMO_PORT` (else `PORT`, else 10000);
- `LEDGERSPY_DEMO_<LIMIT>`;
- Stage 3 only: `LEDGERSPY_DEMO_STORAGE_URL`, `LEDGERSPY_DEMO_STORAGE_BUCKET`,
  `LEDGERSPY_DEMO_STORAGE_SERVICE_KEY` (secret).

**Handling rules.**
- **Generating the session key:** generate it once, locally, e.g. `python -c "import secrets;
  print(secrets.token_urlsafe(48))"`. Put it **only** in the hosting dashboard's environment settings.
- **Keeping secrets out of everything visible:** never in the repository, deployment files, build logs,
  screenshots or the browser.
- **Rotation:** rotating the session key invalidates every workspace cookie and token. Visitors get new
  workspaces; old ones expire normally.
- **Redaction:** settings objects never print secrets (tested).

## 9. Supabase Storage (Stage 3, implemented; not yet run against a real project)

- **Bucket:** **private**; checked at start-up, a public bucket disables persistence.
- **Key:** the secret (service-role) key stays on the server: sent only to the configured https origin by the
  standard-library client, never logged, never in an error message, a response, a snapshot or the browser.
- **Requests** (Supabase Storage REST API, as used by `supabase/storage-js`): create-only upload
  `POST /storage/v1/object/<bucket>/<key>` with `x-upsert: false`; download `GET …/object/<bucket>/<key>`; list
  `POST …/object/list/<bucket>`; delete `DELETE …/object/<bucket>` with `{"prefixes": [...]}`. Every request has a
  30 s timeout; 5xx and network failures are retried twice; responses are size-capped.
- **Object keys** are generated server-side from validated workspace IDs only and checked before every request:
  `workspaces/<W-id>/snapshot-<12-digit generation>.zip` and `workspaces/<W-id>/manifest-<generation>.json`.
- **Retention:** hourly (and at start-up) the service deletes, folder by folder and only through that folder's
  validated keys, the objects of workspaces older than 7 days (by the server-written `workspace_created_at`, or by
  Supabase's own object timestamps plus a day) and orphaned uploads without a pointer older than a day.
- **Pausing:** a free project pauses after a week without activity; restores then fail as "temporary" and the
  service keeps working without saved copies.

## 10. Free-hosting risks (checked 2026-10-15; re-check before each deployment)

**Render free web service.**
- **Capacity:** 512 MB RAM, 0.1 CPU, a single instance, 750 instance-hours a month, about 5 GB of outbound
  bandwidth.
- **Sleep:** it sleeps after 15 minutes idle (about a minute to wake), and the local disk is **ephemeral**: wiped
  on restart, redeploy or sleep. In Stage 2 every such event loses all visitor work.
- **Memory:** each resident workspace app holds its cached results (about 30 MiB measured after the main
  analyses) and, while writing, up to about 1.2 × its database cap of dirty pages (about 30 MiB). With two
  resident workspaces and one PDF job at a time this stays well under 512 MB in the measured paths, but the
  PDF worker and Tesseract still have no memory cap (P20 / P21), and XLSX parsing memory is bounded only
  through the 16 MiB uncompressed-archive limit (an estimate, not measured at the limit).

**Supabase Free.**
- **Limits:** 1 GB storage; pauses after a week without activity.
- **Policy changes:** free tiers change without notice. A change can stop the demo; it must never trigger an
  automatic paid upgrade. No payment method should be attached.
- **No SLA:** the demo can be unavailable, slow or lose work. The UI says so.

**Banner.** Every page of the demo shows, in a sticky bar that cannot be dismissed: "Public demo — synthetic
data only. Do not upload real financial, personal, or confidential data." and "Work in this demo is not saved
across service restarts and is deleted after at most 7 days." The banner is a warning; it does not and cannot
stop anyone uploading real data.

**Trusted proxies.** Per-client creation limits key on the TCP peer, or with `LEDGERSPY_DEMO_TRUSTED_PROXY_HOPS`
= N on the N-th `X-Forwarded-For` entry from the right; `Forwarded`, `X-Real-IP` and entries further left are
never trusted, and uvicorn runs with proxy headers off. Behind a proxy with hops = 0 every visitor shares one key,
so the per-client limit then acts as a second global limit; the service-wide creation rate and the
active/resident caps are the limits that hold whatever the client claims.

**Known risks after Stage 3.**
- **Persistence is best effort and untested against a real Supabase project.** Changes since the last save are
  lost on a restart; a paused or unreachable project means no saves and no restores.
- **Linux:** the Linux-specific paths (`RLIMIT_FSIZE`, `killpg` of worker sessions, `fcntl.flock`, SIGTERM,
  `rmtree` cleanup, symbolic links, Tesseract's temporary folder) were tested on Linux — WSL Ubuntu 24.04 and the
  container image — not on Render itself. The worker cleanup needs an init process as PID 1 (`tini` in the
  image): without one, killed descendants stay zombies and their folders are kept until the next start.
- **Windows:** no OCR and no page images (the file-size limit cannot be enforced); the cleanup walker has a
  residual race against a local writer inside the data folder.
- **Process trees:** a descendant that leaves its process group / session (or a Windows process that escapes
  `taskkill /T`) could survive a timeout; on POSIX its folder is then kept (not deleted under it) until the
  next start.
- **Memory** of the PDF worker, Tesseract and openpyxl is not capped by the demo (estimates above).
- **Retries without a key** are not deduplicated; the offline UI sends no key.
- **Counters** (rates, idempotency entries, failed-workspace records) are in memory and reset on restart.
- **Release bundle:** the offline-bundle check installs the existing release zip, which predates this branch's
  code; rebuild from a clean commit before any release.

**Known limitations (Stage 2).**
- Without storage settings, a restart, redeploy or sleep loses every workspace.
- Stage 2.8 bounds: the PDF render bound is enforced on Linux only (an estimate on Windows); the SQLite
  temporary-file and openpyxl statements rest on their documentation and code; a race with a local writer
  inside the data folder during Windows cleanup remains possible. When SQLite refuses a write, the offline
  `transaction()` helper's own ROLLBACK reports "no transaction is active" (SQLite already rolled back); the
  front door recognises the refusal in the exception chain and answers `507 storage_limit_reached`.
- The unchanged UI shows a `504 still_processing` message as error text; it does not poll for the outcome.
- The rate limits and the record of failed workspaces are in memory and reset on restart.
- The string-similarity caches are shared (§2.1).
- Requests to one workspace are fully serialised, so a slow analysis blocks that visitor's other requests.
